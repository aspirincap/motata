# Motata Report

## Role

Use this as the Motata reporting layer. Motata skills own platform access and ad semantics; `$motata-report` owns dataset validation, analysis structure, chart/table reasoning, audit, and HTML-first reporting.

Trigger this skill for formal Motata reports even when the user does not mention UDA.

## Core Contract

- Default final artifact: HTML.
- Treat Markdown as secondary unless the user asks for Markdown.
- Do not paste full reports in chat; return a concise summary plus the HTML path.
- Preserve Motata context: platform, account IDs, date range, timezone, user type, metric preset, coverage state, attribution window, sampling state, and enrichment state.
- Treat platform data as directional when attribution, modeled metrics, SKAN, SAN, W2A redirects, or missing first-party truth are involved.
- Never include access tokens, API keys, auth headers, or raw token payloads in final artifacts.

## Recommended Inputs

External agents should pass a compact report request instead of vague prose.

Minimum input:

```json
{
  "platform": "meta | tiktok",
  "account_id": "Meta ad account ID or TikTok advertiser ID",
  "access_token": "token or token-source reference",
  "period": "daily | weekly | custom",
  "depth": "fast | standard | full | deep",
  "timezone": "account/reporting timezone when known",
  "known_user_type": "optional confirmed vertical",
  "output": "html"
}
```

For `period=custom`, also pass:

```json
{
  "since": "YYYY-MM-DD",
  "until": "YYYY-MM-DD",
  "previous_since": "YYYY-MM-DD optional but recommended",
  "previous_until": "YYYY-MM-DD optional but recommended"
}
```

Interpretation rules:

- `period` is the date window. `daily` means yesterday vs the day before; `weekly` means last 7 complete days vs previous 7 complete days.
- `depth` is data completeness, not daily/weekly. Use `fast` for speed, `standard` for routine reports, `full` for formal复盘, and `deep` for audit/debug.
- If the token is missing, use `motata-token` first. Do not place raw tokens in report HTML.
- If user type is unknown, use the platform `user_type` source generated by the report runner.

## Completeness and Artifact Boundary

`motata report ... run` collects evidence and writes a manifest; it does not itself promise a finished HTML document. Render and audit HTML as a separate step, and only return an `html_path` after checking the artifact exists.

Inspect execution status, warnings, failed sources and pagination completeness even when files were produced. A degraded or truncated dataset cannot support an unqualified full-account ranking or automated budget action. Keep unknown-currency accounts isolated and never add unlike currencies. Preserve account timezone, attribution windows and metric fallback details in the report limitations.

## Recommended Data Pull

Prefer these first-class report runners before generating HTML:

```bash
motata report meta run \
  --account-id "$META_ACCOUNT_ID" \
  --access-token "$META_ACCESS_TOKEN" \
  --period weekly \
  --depth standard
```

```bash
motata report tiktok run \
  --advertiser-id "$TIKTOK_ADVERTISER_ID" \
  --access-token "$TIKTOK_ACCESS_TOKEN" \
  --period weekly \
  --depth standard
```

Use `--dry-run` when you only need to inspect the planned sources. `standard`, `full`, and `deep` runs include targeted previews by default; use `--no-previews` only when speed is more important than Creative preview completeness. Preview enrichment must stay targeted to final/top report ads, not a full-account deep fetch.

## Recommended Outputs

The final response should return a small result object in prose, not a pasted report:

- `html_path`: primary HTML artifact.
- `run_dir`: `build/report_runs/...` source directory.
- `manifest_path`: `run_dir/manifest.json`.
- `period`: current and previous windows.
- `depth`: `fast`, `standard`, `full`, or `deep`.
- `coverage`: full, batch, partial, sampled, or degraded.
- `topline`: spend, revenue, ROAS, result/purchase, and CPA/CVR when available.
- `degraded_sources`: failed or fallback sources.
- `verification`: audit status and any remaining caveats.

## Workflow

1. **Scope and data pull**
   - Use `motata report meta run` or `motata report tiktok run` for routine report data pulls.
   - Use `motata-token`, `motata-ad-ops`, `motata-vertical-analyst`, or platform CLI commands only for supplemental data.
   - Materialize every data source under `build/report_runs/<platform>_<account>_<period>_<depth>_<until>/`.
   - Include platform Activities/Changelog source for the full analysis window (previous + current) so report conclusions can explain changes caused by budget, status, campaign, ad group, ad, creative, or other account operations, except for GMV Max-first reports where changelog/activity sources are not useful and should be skipped.
   - For weekly reports, default to the last 7 complete days and the prior 7 days unless the user gave dates.

2. **Motata context**
   - Classify or confirm user type.
   - Run metric preset recommendation for the platform and user type.
   - Record whether coverage is full, batch, partial, sampled, or degraded.
   - Use `activities` as context, not KPI truth: cite it to explain sudden spend/ROAS/volume changes when relevant, and keep it out of the report if it only adds noise.
   - For Meta, use batch landing analysis first; fetch ad content previews only for ads that appear in the final report.
   - For TikTok auction or hybrid reports, decide final report ad/creative rows from the normal insights pull first, then run creative-retention/asset enrichment only for those final ad IDs. For GMV Max-first reports, decide final product/creative rows from GMV Max report sources first, then run only the targeted GMV Max preview/product enrichment needed by rendered rows.
   - TikTok report auto mode must detect GMV Max-first accounts. For GMV Max-first accounts, GMV Max report sources are primary; traditional auction campaign/adgroup/ad sources are optional probes, not required coverage. Do not mark a GMV Max-first report degraded merely because ordinary campaign/ad/adgroup/landing/creative-retention sources are empty or skipped.
   - GMV Max reports do not need TikTok changelog/activity sources. Current changelog probes do not return useful GMV Max campaign activity in tested accounts, so GMV Max-first reports should not pull `activities`, `activity_targeted_insights`, `activity_daily_breakdown`, or `activity_factors`; missing activity is not a limitation for GMV Max report quality.
   - GMV Max campaign discovery uses `PRODUCT_GMV_MAX` / `LIVE_GMV_MAX`, while GMV Max report filtering uses `PRODUCT` / `LIVE`; keep these API enum surfaces separate.
   - For TikTok GMV Max product/creative reports, interpret `item_id=-1` as `PRODUCT_CARD`, not a concrete video creative and not an unknown item. Preserve or add `item_scope` with `PRODUCT_CARD` for `item_id=-1` and `SPECIFIC_ITEM` otherwise, and separate product-card rows from specific-item creative rankings. Creative ranking should aggregate by concrete `item_id` across campaigns/item groups and default to playback metrics such as product impressions/clicks and video view rates when the API supports them.
   - GMV Max metric requests must be level-specific and use only documented fields. Account supports `cost`, `orders`, `cost_per_order`, `gross_revenue`, `roi`, `net_cost`; product campaign/day supports `roas_bid`, `cost`, `net_cost`, `orders`, `cost_per_order`, `gross_revenue`, `roi`; product/item-group supports `product_status`, `orders`, `gross_revenue`; creative performance pulls support `creative_delivery_status`, `cost`, `orders`, `cost_per_order`, `gross_revenue`, `roi`, `product_impressions`, `product_clicks`, `product_click_rate`, `ad_click_rate`, `ad_conversion_rate`, and video view-rate fields; title/account/content attribute fields are not requested in the default three-dimension performance pull and must come from a documented attribute/status source or preview enrichment; duration supports `cost`, `orders`, `cost_per_order`, `gross_revenue`, `roi`, `roas_bid`. Creative-level dimensions must use documented groupings: `["campaign_id","item_group_id","item_id"]`, `["campaign_id","item_group_id","item_id","stat_time_day"]`, or `["item_id","stat_time_day"]`; single `["item_id"]` is not the default creative pull.
   - GMV Max Product / Item Group report cards should use a hybrid source model. Product identity comes from `/store/product/get/` (`motata tiktok gmv-max-products list`): render the first column as a compact product cell with local-cached product image, product title, `item_group_id`, and pricing (`min_price` as 折后价, `max_price` as 定价). Do not display `gmv_max_ads_status` in the report card.
   - Product status comes from Product-level `product_status` and must be shown as compact color-coded badges: `available` green/ok, unavailable/rejected/disabled red/bad, other non-empty values amber/warn, and missing neutral.
   - Product performance should be derived from Creative rows aggregated by `item_group_id`, not from a separate Product-day pull when Creative data already reconciles. Use `cost`, `orders`, `gross_revenue`, `roi`, `cost_per_order`, `product_gpm = gross_revenue / product_impressions * 1000`, `product_impressions`, `product_clicks`, and `product_click_rate = product_clicks / product_impressions`. Only use this derived product performance when Creative coverage is complete enough to reconcile against Product/account totals within rounding tolerance; if Creative rows are missing, sampled, fast-mode, or fail reconciliation, fall back to Product-level official fields (`product_status`, `orders`, `gross_revenue`) and mark derived spend/ROI/GPM/click fields unavailable instead of fabricating them.
   - Keep Product / Item Group column order consistent with other GMV Max cards: `产品 / Item Group`, `状态`, `Campaign 数`, `消耗`, `订单`, `总收入`, `ROI`, `平均下单成本`, `Product GPM`, `商品展示`, `商品点击`, `商品点击率`. Use a wide table with `.table-wrap { overflow:auto; }`, explicit `product-table` `min-width`, non-wrapping numeric columns, and the same compact-cell treatment used by the Creative `素材 / 账号 / 帖子` column so the product image remains visible while metrics can scroll horizontally.
   - GMV Max creative judgement must not use a blunt "high spend + low ROI = delete" rule. Classify item-level creative buckets into learning/observe, CPM-watch, front-end seeding, decay replacement, replacement candidate, stable keep, or monitor. Protect: new rows that were absent in the previous period and still have normal CTR/view-rate; rows with acceptable Product GPM but temporarily expensive CPM; and rows with weak own ROI but strong click/view signals while account-level ROI remains healthy. Escalate only when a formerly healthy item becomes high-spend low-ROI with a clear period-over-period ROI drop, or when high spend low ROI has no Product GPM/interaction protection. Product GPM is a report-derived metric: `gross_revenue / product_impressions * 1000`. Do not request or display 广告 GPM unless TikTok later documents an ad-impression field for this GMV Max creative endpoint. Recommended action should be new-old material replacement: prepare 5-10 differentiated hooks, run old and new together for 1-3 days, then release budget around day 4-5 if new assets can take over.
   - For GMV Max Creative preview enrichment, first use each report row's `campaign_id_filter`/campaign owner to call `/campaign/gmv_max/info/`, then map `item_list[].item_id` to `item_list[].video_info.video_cover_url` and `preview_url`. The CLI surface is `motata tiktok gmv-max-campaigns item-previews --campaign-id ... --item-id ...`; this is the preferred report source because it preserves the campaign-item-video relationship. Treat missing items explicitly: `campaign/gmv_max/info` reflects the campaign's current item/video configuration and may omit historical, removed, unavailable, or no-longer-delivering creative rows that still appear in GMV Max performance reports. `AUTO_SELECTION` campaigns often return `item_list=[]`; if the same `item_id` appears in any `CUSTOM_SELECTION` campaign's `item_list`, use that same-item preview as a cross-campaign fallback and record the source campaign/item_group when possible. For CUSTOM_SELECTION items, campaign info usually already has `identity_info.identity_type`, `identity_id`, `identity_authorized_bc_id`, `user_name`, and `profile_image`; keep these campaign-info identity fields as the author source of truth. Use `/identity/video/info/` as a targeted, batched supplement when campaign info has identity fields and the report needs fresher poster/video URLs or missing text: group rows by `(identity_type, identity_id, identity_authorized_bc_id)`, send up to 20 `item_ids` per request, include `identity_authorized_bc_id` for `BC_AUTH_TT`, and avoid full-campaign all-item enrichment unless the user explicitly asks for it. For report HTML, keep the post link stable as `https://www.tiktok.com/@motata/video/{item_id}` unless explicitly requested otherwise; TikTok redirects it, while real resolved author URLs can be stored as diagnostic metadata.
   - GMV Max preview enrichment is a separate data-collection step. Prefer campaign-item mapping, then targeted identity/video lookups. The installed HTML renderer only reuses existing API and `gmv_max_resolved_item_previews.json` data by default; it does not depend on an untracked local resolver script. Missing previews must remain visibly unavailable, not fabricated.
   - For GMV Max customized post previews, use `/gmv_max/creation/custom_anchor_video_list/get/` only as an optional fallback for customized TikTok posts. The CLI surface is `motata tiktok gmv-max-custom-anchor-videos list`; a zero-match result is acceptable because the endpoint only covers customized posts.
   - For Product GMV Max authorized/AUTH_CODE post discovery, use `/gmv_max/video/get/` as a diagnostic/source-pool endpoint, not as a standalone report section. The CLI surface is `motata tiktok gmv-max-videos list`; do not force `need_auth_code_video=true` by default. Use `--need-auth-code-video` only when explicitly querying AUTH_CODE posts, or `--identity-list-json` for BC/TTS identities. Do not add videos that cannot be joined back to report `item_id` into the Creative table or a separate report section.
   - Only output period-over-period conclusions when both current and previous source files exist and the date windows are equal length; otherwise label the report as single-period.

3. **UDA validation layer**
   - Validate source files before report writing: loadability, row counts, required KPI fields, parseable numeric fields, preview fields, and data gaps.
   - Produce or embed a data-quality section in the HTML.
   - When the task includes external business data, apply UDA-style joins, cohorts, LTV, margin, lead quality, or non-platform truth analysis inside `$motata-report` rather than routing away from Motata.

4. **Report generation**
   - Build an HTML report with: scope, quality/coverage, KPI snapshot, vertical diagnosis, drivers, Creative/ad tables, audience/landing/funnel sections where available, next actions, and limits.
   - Creative/ad rows must include an inline `Preview` image column; preview links should be available from a hover/focus action on the preview image rather than a standalone URL column.
   - GMV Max Creative table rendering must not hard-code a tiny Top 15 cutoff for preview availability. Keep the full preview map in memory, render a configurable Creative table limit (default at least Top 40 for weekly reviews), and cache preview images for every rendered row. Important reviewed items outside the default rank cutoff should be includable via `--creative-limit` or an explicit target list.
   - Render GMV Max with `motata report render-gmv-max --run-dir <run> --out <report.html>`. Generation is offline by default. If image downloading is authorized, add `--cache-images`; otherwise explain that remote signed image URLs may expire or require internet when viewing. Existing local cached image paths remain usable without network.
   - Reuse the shared Motata HTML helpers in `motata_cli.report.html_utils` for report tables, preview cells, and table CSS. Wide tables should use `.table-wrap { overflow:auto; }`, stable preview dimensions, named table classes such as `creative-table`, explicit `min-width`, non-wrapping numeric columns, and wrapping long text/URLs. Do not hand-roll divergent table CSS in one-off report scripts.
   - Long URLs, campaign names, and ad names must wrap inside table cells.
   - Keep UI dense and operational; avoid landing-page marketing layouts.

5. **Audit**
   - Run `scripts/audit_motata_report.py` against the HTML and run directory.
   - Fix any failed required checks before final response.
   - Add the audit JSON to the run directory when possible.

6. **Final response**
   - Answer in the user's language.
   - Include the HTML path, the source run directory, key KPI summary, and verification status.
   - Mention failed/degraded data sources plainly.
