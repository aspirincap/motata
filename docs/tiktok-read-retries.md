# TikTok 只读限流与退避

2026-11-13，本机 0.3.0 修订；未发布 npm/GitHub。此前实测的 `40100 / Too many requests` 已改为 `rate_limit`，不再触发 Token 认证失效。TikTok [API for Business 错误码文档](https://business-api.tiktok.com/gateway/docs/index?doc_id=1832184306529874&language=ENGLISH) 将 40100 定义为请求过于频繁。

同日补充识别实测响应 `HTTP 200 / code=40002 / message=OVER_QPS_LIMIT`。只匹配这个错误码与完整消息组合（忽略大小写、首尾空白和末尾句点）；其他 40002 参数/Token 错误不会因此被重试，也不依靠 HTTP 状态判断是否限流。

## 默认策略

统一由 `TikTokHTTP.request` 管理，每次逻辑只读请求独立计数：

| 项目 | 默认值/规则 |
|---|---|
| 总尝试次数 | 5 次，包含首次请求，最多重试 4 次 |
| 可重试错误 | `rate_limit`、网络连接/超时、5xx；认证、参数、协议错误不重试 |
| 读写识别 | 使用端点注册表的 `write` 标记；已审核的只读 POST 也可重试 |
| 指数上限 | `min(60, 10 × 2^(失败次数−1))` 秒 |
| 无 Retry-After 时 | equal jitter：上限的一半 + 均匀随机数 `[0, 上限的一半]`；四次等待分别为 5–10、10–20、20–40、30–60 秒 |
| Retry-After | 支持非负秒数和 HTTP 日期。等待为 `max(服务端最小等待, 指数上限/2) + 随机数`，不会提前到服务端要求之前 |
| 累计等待预算 | 最多 180 秒，合计退避和共享节流的 sleep；不包含 HTTP、凭据获取、SQLite 锁等待等执行时间，不是整体超时；不满足下一次等待时直接返回失败 |
| 大于预算的服务端等待 | 不截短后强行请求，保留原 Retry-After 并以 `wait_budget` 结束 |
| 无效 Retry-After | 无效日期、负数、NaN/Infinity 忽略，回退到指数退避；过去日期视为 0 秒，再应用本地退避 |
| 提示 | 等待前向 stderr 输出次数、等待时间、端点及类别，stdout JSON 不变，不输出 Token、账号或请求内容 |

请求响应先关闭，再等待。相同请求参数在重试中保持不变；正常过期的 Auth Center lease 可在下一次尝试重新获取。每次实际平台请求单独记录用量；用量上报未知或被阻止后，后续平台请求停止，不重报历史用量。

创建、更新、状态改变、上传、任务创建始终只发送一次，即使收到 40100、429、5xx 或连接超时。写前账户证明属于独立只读请求，可退避；它不会导致写入请求被重放。既有 unknown/reconcile/resume 机制保持不变。

## 跨请求、跨进程共享节流

同一 `MOTATA_HOME` 下的 Python 与 npm CLI 共用 SQLite 状态，默认文件为 `~/.motata/tiktok-read-limits.sqlite3`。按 API 主机、版本、HTTP 方法、端点路径分桶；同一端点的不同账号与 Token 共享一个桶，不同端点互不阻塞。Direct Token 无法可靠给出开发者 App ID，因此这里没有猜测平台的账号/App 配额维度。

| 项目 | 本地规则 |
|---|---|
| 正常读取 | 相同端点的请求准入间隔至少 1 秒 |
| 审核信息读取 | 路径以 `/review_info/` 结尾时至少 2 秒，包含普通与 Smart+ 审核接口 |
| 限流冷却 | 将本次 Retry-After/指数退避/抖动计算得到的期限写入共享状态，只延长、不缩短已有冷却 |
| 次数或预算耗尽 | 即使最后一次失败后不再重试，也发布冷却期限；随后启动的 CLI 仍需遵守 |
| 并发与唤醒 | SQLite 短事务原子抢占准入时隙；睡眠后重新检查期限，遵守其他进程刚延长的冷却。睡眠、取凭据和平台请求期间不持有数据库锁 |
| 等待预算 | 与本次 HTTP 重试共用 180 秒；一次退避已等完的时间不会再等一遍。若首次发送前就因共享期限超预算，`attempts=0` |
| 成功与网络错误 | 成功不会清除其他请求发布的冷却；网络错误只做自身退避，不发布额外共享限流冷却 |
| 状态不可用 | 文件损坏/目录不可写/锁超时等返回 `limiter_error`，停止后续发送，外层不重试；若已有平台错误则保留它及实际尝试次数 |
| 持久化与隐私 | 只保存端点及两个时间戳；不保存 Token、账号、请求参数或响应。POSIX 文件权限为 0600 |

准入等待发生在平台用量事件准备之前，不会把等待计作平台请求。等待后重新检查 Auth Center lease，必要时刷新再发送。直接写入与上传不进入共享读队列、不自动重试；写前账户证明仍遵守读策略。`--retry 1` 只禁止失败后的重试，首次请求仍需遵守共享节流。

1 秒/2 秒是本机保守策略，**不是 TikTok 官方 QPS 保证**。此方案不跨机器、不覆盖其他 `MOTATA_HOME` 或外部调用方，也不推断各端点是否共享服务端内部配额；应用配额耗尽、平台内部限制或持续限流仍可能导致最终失败。数据库使用系统时间协调进程，系统时钟跳变可能影响冷却长度，等待预算仍限制本次 sleep 总量。

## 单一重试层

- TikTok 报表与落地页报表移除 `request_with_retry` 包装；报告的 `run_source` 不再整段重新执行，避免成功页及任务提交重复。
- 所有传输层失败带 `retry_managed` 标记，兼容的通用 helper 遇到该标记直接传播异常，不重新分配预算。
- 报告 manifest 的 `attempts=1` 表示数据源执行一次；失败时另记录 `http_attempts` 和 `retry_stop_reason`。
- Meta 的报告重试次数和等待参数保持原样。此变更不涉及其他平台的调度策略。

## 报表参数

`motata report tiktok run --retry 5 --retry-wait 10` 现在分别表示**每次只读 HTTP 请求的总尝试次数**和**首次指数退避上限**；不再表示整份数据源重放次数和固定间隔。`--retry` 范围为 1–10，设为 1 可禁止自动重试；`--retry-wait` 必须为有限非负数。普通 TikTok 列表命令使用默认策略。Python 调用者可通过 `ReadRetryPolicy` 配置等待预算及上限。

## 验证与边界

回归覆盖错误分类、秒数/HTTP 日期、抖动范围、预算耗尽、响应关闭、中断、GET/只读 POST、全部注册写端点、上传、Auth Center 不误失效/逐次计量/到期刷新，以及报表分页不重放。本轮新增 26 项测试，包含 5 个独立进程竞争、跨进程冷却恢复、并发延长期限、最后一次失败共享冷却、状态故障及等待期间凭据刷新。Python 3.11/3.14 各 475 项全量回归通过；使用假响应、真实临时 SQLite 和模拟时钟/等待，不依赖真实限流。

达到预算后仍可能失败；不会为等待限流恢复无限阻塞。先前真实账户读取记录只能证明接口可用，自动退避和共享节流的正确性以本轮受控回归为准。本轮没有请求真实 TikTok 账户，也没有远程写操作。
