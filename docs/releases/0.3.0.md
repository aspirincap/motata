# 0.3.0 — TikTok Direct HTTP

Release notes for `motata@0.3.0`. Publication status is recorded by the matching GitHub Release and npm registry entry.

## npm distribution

The npm package now declares its GitHub repository. Version-tag releases use GitHub Actions OIDC with provenance and publish the exact tarball accepted by the release gate. No long-lived npm publish token is configured in the workflow.

npm 12 installations work with the default disabled install-script policy: the first `motata` command bootstraps the Python runtime, and subsequent commands reuse it. Python 3.11+ remains required. The release workflow tests a clean npm 12 global install before publication and checks the registry installation afterward.

## Authentication and configuration

TikTok now uses Auth Center **v0.3.9** API Keys to obtain platform credentials in process, then sends requests directly to `https://business-api.tiktok.com/open_api/v1.3/`. This path needs no JWT, gateway process, device login or gateway extra dependencies.

Configure `AUTH_CENTER_API_KEY` through the process environment. `AUTH_CENTER_BASE_URL` defaults to `https://motata.one`; HTTPS is required except for an explicitly configured loopback development service. The default header is `X-API-Key`; `--auth-center-header bearer` selects the existing API Key bearer form. This is not a JWT.

```sh
motata init --platform tiktok --token-source auth-center --account-id YOUR_ACCOUNT_ID
motata tiktok campaigns list --account-id YOUR_ACCOUNT_ID
motata report tiktok run --account-id YOUR_ACCOUNT_ID --period daily --depth standard
motata capabilities show tiktok
```

Existing `--access-token` and `TIKTOK_ACCESS_TOKEN` / `MOTATA_TIKTOK_ACCESS_TOKEN` are retained for explicit platform-token use. Explicit `--access-token` conflicts with explicit `--token-source auth-center`. A saved auth-center profile never falls back to a different platform token after a Key/account error. A saved direct profile remains direct until the user changes its token source.

Profiles store the origin, header mode and credential source, not the Key or tokens. Command-local leases expire after at most 60 seconds; known token expiry gets a 30-second margin. Account lookup is tenant-scoped. Before a write, the chosen token must prove access to the advertiser because the v0.3.9 convenience endpoint may return a channel fallback token. Multi-account requests select separate credentials by account.

Auth Center's API Key has full access to its own tenant's OpenAPI. Its server still checks Key validity and tenant ownership. Previously delivered TikTok tokens are not instantly revoked by changing the client configuration or revoking an API Key.

## HTTP coverage and compatibility

- All 74 original public methods are retained. All 51 former SDK operations and 31 existing HTTP contract cases have offline request fixtures; the registry contains 83 endpoints including native-series discovery.
- SDK loading, external/vendor fallback, the SDK gateway bridge and vendored SDK source are removed. `requests-toolbelt` provides bounded-memory multipart uploads; `six` is no longer a direct dependency.
- JSON preserves unknown fields, false, zero, null and explicit empty collections. Optional `None` query/form parameters are omitted. HTTP 200 still requires a successful TikTok business code.
- Errors carry HTTP status, platform code/trace, category and write outcome. Transport never automatically retries writes or switches implementation. As of the 2026-11-13 local revision, the HTTP transport is the sole retry owner for read-only requests, including reviewed read-only POST endpoints; report/landing-page wrappers no longer replay requests or whole sources. `40100` is correctly classified as a rate limit, not an authentication failure.
- File and URL uploads use separate validation; `--file` is no longer mandatory with `--video-url` / `--image-url`. Explicit upload_type must match file/URL input.
- Smart+ MINIS payloads bypass ordinary iOS App normalization. Copy payloads preserve native series, distribution and identity fields.
- Explicit TikTok gateway mode fails at entry. Existing Meta and separate Gateway code is not converted to anonymous access.

The [endpoint matrix](../tiktok-endpoint-matrix.json) records the migration baseline and original documentation provenance. The historical vendor's upstream revision was unverified; request fixtures preserve the checked local behavior without shipping that code.

## Usage reporting and recovery

Each actual platform call using Auth Center credentials records a non-secret event in `~/.motata/auth-center-usage.sqlite3` (or `MOTATA_HOME`). Pagination and actual retries count separately. Calls known not to have been sent are not reported. Platform timeouts that may have reached TikTok count as one attempted token use.

Auth Center v0.3.9 does **not** deduplicate usage reports by request_id. Unknown reporting outcomes are saved and never automatically reposted. Reporting failure cannot change or replay the completed advertising request; later platform calls in that run stop. Inspect/reconcile the event with Auth Center administration before resuming operational work. A crash may leave `platform_pending` or `sending` records; these also require reconciliation, not blind replay. Manual platform-token mode does not invent Auth Center billing attribution.

Ordinary campaign copy now returns a `job_id` and durable step records. Retain the ID to reuse completed objects:

```sh
motata tiktok smartplus-campaigns copy SOURCE_ID --name COPY_NAME --account-id ACCOUNT_ID --job-id COPY_JOB
motata tiktok smartplus-campaigns copy SOURCE_ID --name COPY_NAME --account-id ACCOUNT_ID --job-id COPY_JOB --resume
```

`--resume` retries only confirmed failed steps and verifies saved successes. Unknown/submitting writes are blocked. A changed payload under the same step or a changed job configuration is rejected. Copy recovery does not automatically reconcile unidentified remote objects. Local state lives in `~/.motata/jobs/tiktok-operations.sqlite3`; retaining it is necessary for cross-process recovery.

## Drama Series workflow

New commands: `motata tiktok drama-series list`, `plan`, `validate`, `create`, `resume`, `reconcile`.

Input contains `advertiser_id` and separate `campaign`, `adgroup`, `ad` objects. Supply campaign/group names, budget_mode/budgets, deep_bid_type, schedules, targeting_spec, authorized identity, creative_list[].creative_info and ad_configuration.call_to_action_id. Omit `ad_name` or set it to `""` for a platform-generated name. Omitted creative identities inherit the selected group identity; a different, fully specified authorized creative identity is supported and checked independently. The planner fixes `APP_PROMOTION + MINIS`, `NATIVE_SERIES + VALUE + AD_REVENUE_VALUE`, and sets every created object to `DISABLE`. It does not invent account eligibility or choose creatives for the user.

Owned mode uses `adgroup.native_series_id`. Distribution mode uses `adgroup.drama_selling_setting` with an absolute HTTP(S) distribution_link issued by the copyright holder in Drama Center. These branches are mutually exclusive even when a supplied value is null or empty. `BC_AUTH_TT` additionally requires identity_authorized_bc_id. Ordinary TikTok payload-file/JSON entry points remain available for fields without dedicated flags.

```sh
motata tiktok drama-series plan --payload-file drama-input.json --out drama-plan.json
motata tiktok drama-series validate --plan-file drama-plan.json
motata tiktok drama-series create --plan-file drama-plan.json --job-id DRAMA_JOB
motata tiktok drama-series resume --plan-file drama-plan.json --job-id DRAMA_JOB
```

Planning is local. Validation reads account, group/creative identities and (for owned mode) series access. Creation performs real writes despite DISABLE, checkpoints each successful ID, and checks returned IDs, advertiser, parent and disabled status. Generated names appear in `resolved_names`; resume reuses saved IDs. Confirmed failures can be explicitly resumed; unknown outcomes must first be resolved. To reconcile an explicitly identified existing object, use `reconcile --plan-file ... --job-id ... --step campaign|adgroup|ad --object-id ...`; the object must match the saved name, status and parent before its ID is accepted. For an autogenerated ad name, reconcile compares supplied creative asset/identity fields and the dynamic CTA instead of relying on the name.

Account allowlists, distribution authorization and full creative eligibility remain authoritative at TikTok. The planner checks CBO/adgroup budgets, shared settings, bidding, UTC schedules, nested targeting/creative identity and dynamic CTAs. Target-ROAS preflight scans existing groups/campaigns for the same series and overlapping location/zip IDs; country/city hierarchy overlap still needs platform validation. Smart+ adgroup updates reject the reviewed create-only identity, series, promotion and optimization fields while preserving unknown new fields. A successful local plan or read-only validation is not proof of campaign approval or delivery eligibility. Creating a disabled object does not approve or activate it.

Smart+ adgroup updates are incremental: only `advertiser_id` and `adgroup_id` are required. Conditional changes (budget, bidding, schedule, targeting, search and related controls) first read the group and campaign; those snapshots are used only for validation and never merged into the outgoing request. Rename and plain comment/share patches do not need these reads. Each actual read counts toward Auth Center usage. The read and write are separate calls, so concurrent remote changes remain subject to TikTok's final validation.

Update flags support explicit false through `--no-comment-disabled`, `--no-share-disabled`, `--no-organic-comment-disabled` and `--no-suggestion-audience-enabled`. `--budget-auto-adjust-strategy` accepts `AUTO_BUDGET_INCREASE` or `UNSET`. Smart+ update no longer accepts the unsupported `--pacing`; normal adgroup update retains it. Bid/ROAS updates print the documented possible sibling-group impact to stderr without changing the JSON response or synthesizing a different bid field. See the [snapshot review](../tiktok-drama-contract-review.md) for source discrepancies, covered constraints and platform-only checks.

## Capability maintenance

`motata capabilities show tiktok` and `check` display installed endpoint/version/transport information without fetching new execution code. The scheduled `tiktok-contract-watch.yml` workflow is read-only and produces a review artifact for the four Smart+/Drama guide sources.

The monitor normalizes readable official text or structured definitions, saves hashes and diffs, and labels application shells/login/failed pages `source_unavailable` while retaining the previous baseline. Such pages require manual review in the official portal. No automatic merge, SDK update, platform version change or runtime rule download occurs. Expanding document coverage and structured semantic schema comparisons can use the same review flow.

## Verification

```sh
python scripts/run_offline_tests.py
python scripts/check_tiktok_http.py
node --test tests/runtime.test.js tests/runtime-lock.test.js
python scripts/check_release.py --wheelhouse /path/to/offline/wheels
```

The artifact gate audits wheel, rebuilt sdist and npm contents for SDK residue, uses isolated caches, and performs clean Python/npm install checks when a wheelhouse is supplied. Upload tests consume local 50/500 MiB sparse fixtures without network calls. Local testing does not prove the Windows/Linux CI jobs have run.

The [live validation record](../tiktok-live-validation.json) is a public summary with account and platform request IDs removed; original evidence is retained locally outside version control. Credentials were provided to the test process through hidden input, not written to the repository. Live Auth Center verification requires a configured API Key. Real Drama Series creation/update requires eligible identity, series and creative inputs; mock execution/recovery tests do not substitute for that account-specific acceptance.

See the [implementation validation record](../tiktok-http-validation.md) for exact local test counts, environment, live results and remaining acceptance work.

The [read retry policy](../tiktok-read-retries.md) documents the local 2026-11-13 fix: five total attempts by default, exponential equal jitter, numeric/HTTP-date `Retry-After`, and a 180-second cumulative sleep budget. The existing TikTok report `--retry` and `--retry-wait` flags now configure that single HTTP policy; Meta's settings are unchanged.

The same-day follow-up recognizes only the specific `40002 + OVER_QPS_LIMIT` combination as a rate limit, leaving unrelated 40002 failures non-retryable. Read admission and cooldowns now use SQLite shared by CLI processes with the same `MOTATA_HOME`: one-second endpoint spacing, or two seconds for `/review_info/`, plus server/backoff cooldowns that persist even after the final failed attempt. These are conservative local defaults, not documented TikTok quotas. Shared waits consume the same sleep budget; no credentials or account IDs are stored. Writes and uploads still never retry automatically. Python 3.11 and 3.14 each pass all 475 offline tests, including process contention and lease refresh during shared waits.
